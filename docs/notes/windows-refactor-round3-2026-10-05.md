# 第三轮：词库覆盖、混合简拼纠错与搜索候选

## 已确认的原因与改动

beta.4 主词库缺少“环太平洋”完整词条，但全拼可以通过“环＋太平洋”组合输出。用户实际键串为 `huantaipingy`，末尾声母会被整句转换丢掉，导致“还太平”等短句抢在完整候选之前。补入完整词条，并在前音节完整、末尾单声母且词级候选全覆盖时保留完整词的排序。

`nijuedezhegdiayzenmy` 混合完整音节与声母简拼，其中 `dia` 漏了 `n`。旧逻辑因内含简拼而完全跳过音节级纠错，新逻辑允许较长输入的完整音节展开错拼读法，短串和不完整音节仍保守。整串单处纠错上限增至 64 字母；变体比较使用静态单路径，不为每个变体启动模型任务。

补丁词库新增 7 个常用作品名与 8 个常用词，共 15 条，人工校对读音，权重 2000／3000 是排序参数，不是实测频率。并未把评测标准句作为词条加入。

## 冻结评测：关闭模型与云服务

92 种子（72 词、20 句）生成 1,444 条固定组合，逐条保留候选与失败；其中 1,104 条是首／中／尾部的漏键、多键、相邻交换与邻键替换。新旧使用相同锁定主词库、人工读音、配置和静态语言模型。基线二进制与最终二进制、种子及补丁哈希保留于附件。

正常全拼中原先正确的 81 条没有退步，正常输入整串纠正标记为 0；但候选首选仍存在同音词和歧义错误。查询耗时增加，结果是本机优化版本的静态查询计时，不代表 Windows 应用端到端延迟。

72 个被审计词形中最终有 70 个完整词条，缺失“新安、嗲声”；完整词形存在不证明读音／排序正确，缺失也不证明无法组合输入。补词与测试词重合，这个数据是回归结果，不能证明陌生语料或总体词库覆盖率。旧基线未输出词形审计字段，故其覆盖率为 null，而非 0。

用户用例：`huantaipingyang`、`huantaipingy`、`huantpingy` 首选“环太平洋”；`htpy` 首选“和太平洋”，“环太平洋”第三。`nijuedezhegdiayzenmy` 首选“你觉得这个电影怎么样”。输入中的单引号是窗口自动分隔，测试使用原始键串。

仍失败的正常首选包括：耳机→二级、电源→店员、香蕉→相较、知识→只是、西安→先、嗲声→大声、登录→登陆、退出→推出。`woxiangxuexirust` 的无模型混输仍失败，错拼仍有 1 条解析失败。保留这些失败以便后续比较，不把“有纠正标记”统计为成功。

独立的原有期刊主题 336 条集合保持不变：正常首选 12/30（40%）未变，错拼首选由 32/270（11.852%）至 71/270（26.296%），字错误率由 35.320% 至 21.733%。此为无模型对照，不能直接和 beta.4 随包模型的 15/30、34/270 混为一组。

逐键检查两种“环太平洋”、用户混输句和 38 键漏字长句，最慢单键分别为 4.67、0.888、2.25、14.00 ms。另外逐键输入 94 个词句，共 1198 键，最慢单键 13.090 ms。报告见 [本轮逐条附件](windows-refactor-round3-eval/after-summary.json)。

## Windows 搜索栏候选

无代码签名的 beta.4 自绘候选窗无法可靠盖过系统搜索界面。按 [微软 UI-less 协商接口](https://learn.microsoft.com/en-us/windows/win32/tsf/uiless-mode-overview)，补充处理器 Ex、候选 UIElement／Behavior／Integratable 和搜索 FunctionProvider，让愿意接管的宿主绘制列表；其他宿主仍自绘。没有导入根证书或修改系统保护。

显示协商、未变化帧不重绘、页内选择边界、同会话原始键串与文本校验、过期取消／原样上屏拒绝、不可变搜索快照、枚举克隆／短读、结束反注册均有回归。协议 8 的新帧字段保持旧 JSON 默认值，安装后应重启仍加载旧 DLL 的应用。辅码格式兼容门槛固定为版本 7，避免协议升至 8 后把 beta.4 DLL 错误降级。

本机 Core 326 项、Server 引擎闭环 74 项通过，TSF GNU 库严格 Clippy 通过。最终全量适用回归 704 项通过（3 项明确忽略）。先前主分支 Windows CI（37286337914）的 6 项新原生候选／搜索 COM 测试通过；WSL 缺少 MinGW C 编译器，不把本机类型检查算作原生执行。beta.6 的 Windows 门禁已复验通过。

**Win11 底部搜索栏实际候选显示仍需用户同机验收**；COM 接口测试与编译通过不能证明所有 SearchHost 版本都会接管。Win10、浏览器、VS Code、微信同样待实际输入验收。微软拼音总体准确率尚未做同集对照，不能宣称达到其水平。本地模型仍建议保持关闭，用户电脑异响仍需同机确认。

## beta.5 发布门禁拦截与 beta.6

[beta.5 门禁](https://github.com/Yushi-Xing/Yushi/actions/runs/37286748061) 的通用回归和 Windows 全量回归均通过，但真实模型探针在混合错拼输入上超过 15 秒，安装包没有生成或发布，失败标签保留不移动。

本机同数据的独立调试探针逐次计数：普通输入 1 次重排，混输 2 次重排，混合错拼 1 次重排＋1 次生成，尾音简拼 1 次生成；分别约 2.068、1.678、5.589、1.595 秒完成，随后 2 秒内零新增调用。没有观察到重复排队；Windows 共享 runner 的调试推理明显更慢，但该结果不证明用户笔记本异响原因。

beta.6 性能门禁改为 `cargo test --release`，与安装包的优化构建一致，**没有放宽 15 秒限制或停键零新增调用的要求**，并分别输出重排／生成计数。完整词条已能补齐尾音声母时，也跳过不必要的整句生成；“环太平洋”的尾音简拼增加无生成请求回归。本机优化构建探针通过：普通输入 221 ms（1 次重排）、混输 261 ms（2 次重排）、混合错拼 664 ms（1 次重排＋1 次生成），之后 2 秒内零新增调用；尾音简拼 100 ms 的观察窗内零模型调用，且两个用户输入的首选断言通过。Windows 门禁另行执行，软件探针不能证明异响已经消失。

开启真实随包模型后另外发现 `diay` 被抄成英文“Diay”，压过完整中文纠错路径。新增保守排序：完整中文路径覆盖按键时，英文片段未同时命中英文词表与原始键串的生成结果排在中文路径之后；没有完整中文路径时仍允许新专名兜底，纯中文生成及已输入的已知英文保留原优先级。六项回归覆盖这些边界；修复前的对应测试先失败，修复后通过。

[真实模型 CLI 修复前](windows-refactor-round3-eval/user-model-before-ranking.log)首选“你觉得这个Diay怎么样”，[修复后](windows-refactor-round3-eval/user-model-after-ranking.log)首选“你觉得这个电影怎么样”，生成的混输保留为第四候选。模型停键探针同时断言用户两个键串的首选，避免只验证任务收敛而遗漏输出正确性。
